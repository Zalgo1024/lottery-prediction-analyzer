### 4. 回归 baseline 恒失败 —— 已根治（`02f4aac`）

**根因**：baseline `_reg_ref.json` 存了两类依赖「采集当天 CSV 快照」的量——
`Xs_shape` 的行数（= 记录数 − 窗口）和 `preds`（三种单策略在当时最新数据上的输出）。
CSV 每期追加，行数一涨就必然失败：

```
双色球: Xs.shape [3461, 103] != ref [3440, 103]
大乐透: Xs.shape [2882, 99]  != ref [2859, 99]
```

**这不是代码回归，是数据在前进。** 而每次失败都去 `--update-ref` 刷新基准，
等于把「当前行为」固化成新基准，反而会掩盖真正的回归——这才是要防的事。

**修法：数据窗口钉死。** 新增 `scripts/regression_pin.py`，
baseline 记 `_meta.pinned_issue`（各彩种采集时的最新期号），
校验与采集都把输入截断到该期号：

- `records` 按 `期号 <= pin` 过滤。**期号必须按数值比**：`26114` vs `3001`，
  字符串比会翻转。
- `predict` 的输入也要钉：`prediction/engine.py` 顶层是
  `from data.loader import load_lottery`，须 patch **它自己的属性**，
  patch `data.loader` 对已导入的名字无效。
- baseline 缺 `_meta` 时退出码 2 并提示，不再拿全量数据做必然误报的比对。

**顺带修掉两处过期断言**（都是恒失败，与数据无关）：

| 断言 | 错在哪 | 修法 |
|---|---|---|
| v1 vs `train._build_features[0]` | `build_features` 第 i 个样本的窗口是 `records[i+1:i+1+ws]`（08-31 时间方向修正后的语义），脚本却拿 `records[:ws]` 比 → 窗口错位，实测 `max\|diff\|=1.0` | 改用 `records[1:1+ws]`，diff = **0.0** |
| `bf_y` 列数 | 标签是「每个号码一个二分类」，列数 = 号码总数（红+蓝）`49/47`；原断言拿它跟特征维数 `fd1(103/99)` 比，恒 False。`regression_check.py` 里同义那段还是 `if ...: pass` 的死代码 | 改比号码总数，死代码改成真断言 |

**证据**：老 baseline 按 `Xs_shape` 行数反解出采集窗口——双色球 ≤ **26093**（08-13）、
大乐透 ≤ **26091**（08-12），`preds` **一个字没改**。钉死后校验通过，
说明 **8-14 至今这 21/23 期里代码行为无回归**，原失败纯属数据前进。
判别性测试：剥掉 `_meta` 后校验退出码 2 并拒绝比对（证明不是空转）。

## 七、2026-10-21 一轮：静默失真治理（"不天天开也不至于频繁维护"）

用户诉求原话：**"国庆之后没有天天开了，能不能让没有每天开的情况下不至于那么频繁的维护"**。
体检结论：真正难自己发现的不是"算错了"，而是**静默失真** ——
机器在跑、日志全绿、报表照长，但把用户设的 200/38/50/44 悄悄换成 5 注，页面上没有一个字提示。
这轮只治这一类。

### 1. 出号数量填不满（198 ≠ 200）—— 已修

`predict(双色球, groups=200)` 会偶尔只产出 **198** 组。三处结构性收缩叠加：
三策略都从 Top30 热门号抽样（200 组时已饱和）+ 去重要求两两红球重叠 ≤3 + 剪枝第 2 阶段凑不满。
**后果不是少 2 注**：生产复用判据是「pending 组数 == 当前出号数量」，
少注 ⇒ 每轮流水线都判"不一致" ⇒ 重生成 ⇒ **下一期号码被无声改写**（上午晚上两套号）。

修法：`prediction/engine.py::_pad_to_groups()` —— 引擎出口硬性拉平到请求组数
（先回填被剪枝的票，再按 schema 均匀随机补），并写 `补齐统计`。锁在
`tests/test_prediction_group_count.py`（8 例）。

### 2. 冷启重复开火 —— 已修

同一次冷启对双色球触发 2 次流水线、七星彩 3 次（`recover_lottery` + `ensure_pipelines_fresh`
+ worker 事件三方同时开火）。加两道闸：进程级 `_started` 单飞、轮内 `_claim_trigger`
每彩种只触发一次。锁在 `tests/test_maintenance_guards.py`。

### 3. 启动自愈：注数被覆盖无人知 —— 新增

`web/startup_recovery.ensure_pending_groups()`：冷启时核对「滑轨 == 下一期 pending 组数」，
不一致或无 pending 就按滑轨重生成。**这是 5 次覆盖事故的正解** —— 以前数据新鲜时
启动恢复什么都不做，错误的 5 注会原样留到当晚 22:05。

### 4. 一致性徽章 —— 新增（可观测化）

`GET /api/system/invariants`（`web/utils.groups_invariant`，三态：一致/不一致/无预测）+
看板「自动化运行状态」标题旁的常驻徽章。不一致立刻变红并显示 `彩种 实际/滑轨`。

### 5. status.json 瘦身 —— 已修（2509KB → 629KB）

50 条 history 每条都带全量预测号码（双色球 200 组 ≈ 80KB），而 history 的
`predictions` **没有任何消费方**（看板只用 `last_run` / `last_run_per_lottery`）。
改：history 只留前 6 组 + `预测组数`（`HISTORY_PREDICTIONS_KEEP`），完整数据留在
持久映射里；`get_status` 不再让截断副本覆盖完整 entry；旧文件下次写入时一次性迁移。
⇒ 原"剩余待办"里那条"裁掉 predictions 前要先确认前端是否依赖"，**已确认无依赖**。

### 6. flask_stdout.log 乱码 —— 已修

子进程按 Windows 本地代码页（cp936）写进 UTF-8 文件。`run.py` 给子进程注入
`PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8`；`web/app.py` 再对 stdout/stderr
`reconfigure(encoding="utf-8", errors="replace")` 兜一层。

### 7. 顺带修正的两处"温床"

- `web/validators.py::validate_predict_body`：原限死 `1..10`，且把 `groups: null`
  判成非法（直接 400）—— 它既挡住"留空按滑轨解析"，又暗示"手工填 5 注"是正常用法。
  改为允许 null、上限取 `PREDICT_DEFAULTS["max_groups"]`。
- `web/static/js/main.js::runAutoPipeline`：删掉写死的 `groups:5`（10-18 那批未提交改动）。

## 八、2026-10-21 二轮：维护工程化（"不用你亲自去看"）

用户问："维护优化这块还可以怎么做"。定性结论：**项目不缺功能，缺的是
"不用你亲自去看"** —— 维护动作全都还依赖人在线。本轮按这个标准改造。

### 1. 离线体检：谁叫醒那个没人叫的检查器 —— 已修

`scripts/health_check.py` 六项全扫描写得很完整，**但没有任何调用方** ——
它只能被人手动叫醒，等于把"维护"绑死在"人得在线"上。这是本轮最核心的发现。

新增 `web/health_digest.py`（轻量日报，秒级）+ 调度器接线：
- 每日 23:40 跑一次日报（`digest`），**只在有问题时推送**；
  正常静默 —— 一天一条"一切正常"只会被静音，真出问题时反而看不见。
- 周日加跑一次全量体检（`scripts/health_check.py` 六项扫描）+ 日志清理。
- 冷启补报（`maybe_run(cold_start=True)`）：开机第一眼就有结论，
  不必自己去翻六个页面。boot / daily 两个槽位独立，一天各一次。

接口：`GET /api/system/digest?days=7`（与推送同源，口径不分叉）。
诚实边界：`status.json` 是旋转窗口，若已写满且最早一条仍在窗口内，
日报会标 `计数可能偏少`，不把"至少这么多次"说成"全量"。

### 2. 测试计数的手工同步 —— 已自动化

加完测试后，这个数字散在 4 个载体、至少 8 处：README 徽章 / 命令注释 /
说明段 / 结题报告 md（5 处）/ docx / PDF。每加一批测试都要手工数再逐个改，
改漏一处文档就在撒谎 —— 而这恰恰是外人判断项目质量的第一个信号。

`scripts/sync_counts.py`：真源 = `pytest --collect-only -q`（全量 + tests/ 两次）；
带上下文的正则替换（不裸替换数字）；**每条规则零命中即报错**（防"跑成功但没改"）；
docx 只改 `<w:t>` 内部文本且校验节点数不变；`--check` 可进 CI/预检，`--pdf` 顺带重导。

### 3. 依赖浮动 —— 已锁

`requirements.txt` 九行全是 `>=`，等于无约束。最贵的不是代码是 `training/`
与二十年 `lottery_data/`，一次 numpy/lightgbm 大版本跳跃会让它们全部失效，
且错误表现为"数字看着正常但变了"。

`scripts/sync_lock.py` → `requirements.lock.txt`（**42 个包**，只含 requirements
顶层依赖的传递闭包，不把本机 400 个无关包写进来）。更新依赖后重跑并一起提交。

> 顺带发现：`alembic` 是 optuna 的硬依赖但本机未安装（optuna 的 RDB storage
> 不可用）。lock 里如实标注，不补装 —— 装上可能改变现有数值，属需单独决策的变更。

### 4. 配置进不了版本 —— 已修

`git ls-files config/` 曾经是 **0**。原因是 `.gitignore` 一句 `config/`
把密钥和业务配置一起扫掉了 —— 而 `ticket_size.json` 存的是用户亲手设的
「每次出号几注」（200/38/50/44），丢了无法重建。

改 `config/*` + `!config/ticket_size.json`（必须用 `config/*`：目录整体忽略后
Git 不允许再用 `!` 放行其下文件）。`push_notify.json`（含 webhook token）继续排除。

### 5. 测试提速：只做机制，不假装提速 —— 见下

新增 `pytest.ini`：`testpaths = tests scripts`、`--strict-markers`、注册
`slow` / `network` 两个 marker。

**但没有给现有用例打任何 `slow` 标记**，原因值得记一笔：
实测全量 402s，慢点集中在 20 个 13~18s 的用例上，而它们几乎全是
「调一次真实 `predict()` 并落盘 → 断言注数/批号/实得」的**契约测试**。
把它们标成 slow 确实能让快集降到 2 分钟，但也就把「注数恒等于滑轨」
这道防线（2026-10-21 上午刚修的那条）从日常验证里踢了出去。
**为了快而削弱防线，方向错了。** 真要提速应该做 fixture 级数据缓存，
那是另一个量级的改造，不属于"维护优化"。

保留 marker 机制的价值在于：以后新增的**纯诊断性质**重活（全量 MC、跨彩种扫描）
可以打 `slow`，`pytest -m "not slow"` 随时可用，不必再改配置。

`--strict-markers` 不是洁癖：marker 拼错时 pytest 只留一行 warning，
`-m` 选择器静默失效，你以为跑的是快集其实全是重活。

### 8. 明确**不**做的

- **覆盖率门槛**：70 个测试文件已够厚，加门槛只会逼出"为绿而绿"的假测试。
- **全仓 lint 整改**：一次改上百文件，git 历史被噪音淹没，价值为负。
- **Docker / CI 矩阵**：Windows 本地 + 私有仓库，投入远大于收益。
