## 二、发现并抢救了一处数据损坏：排列3 历史

### 现象

`training/feedback/排列3_feedback_history.json`（2,354,307 字节）的结构是：

```
偏移 0        : "[]"
偏移 2        : 368,449 个 NUL 字节
偏移 368,451  : 一条记录的中段 …
偏移 2354306  : "]"（文件正常结束）
```

即**前 368KB 被 `[]` + NUL 覆盖**，后面 198 万字节完整。

### 根因：两条，任一单独存在都不致命，合起来就是永久丢数据

**① 写入非原子**（`data/feedback.py::_safe_write_json`）

```python
with open(path, "w", encoding="utf-8") as f:     # ← 立刻把文件截断为 0
    json.dump(data, f, ...)                      # ← 流式写，中途被杀就是半截
```

进程中途被杀 / 磁盘异常时，NTFS 上留下这种"头部空、尾部在"的空洞形态。

**② 读取损坏时静默按空**

```python
except (json.JSONDecodeError, ...) as e:
    logger.warning(...)      # 只打日志
    return default           # ← 返回 []
```

调用方 `append_feedback` 紧接着 `history.append(...)` 再 `save_*` 写回
⇒ **损坏文件被空列表覆盖，抢救窗口为 0**。

### 抢救结果

从残尾读出 **1,611 条**（期号 26236~26283，2026-09-03 ~ 10-24），
与 `_backup_20260911/` 的 **853 条**（26212~26243）合并去重后得到 **2,069 条**
（26212~26283，2026-08-10 ~ 10-24），已原子写回并回读校验。

- 损坏原件归档在 `training/feedback/_backup_20261024_corrupt/`
- 抢救脚本 `scripts/oneoff/_rescue_pa3_history.py`（可重复运行，`--dry-run` 先看）
- **丢失部分**：26212 之前的历史在备份里也没有，不可恢复。
- 剩余期号缺口 16 处（26213、26220~26225 等），这些在备份与残尾里都不存在，
  属于历史空档，不是本次丢失。

### 修复

| 改动 | 位置 | 目的 |
|---|---|---|
| 原子写（tmp + fsync + os.replace） | `_safe_write_json` | 读者只会看到旧的完整版本或新的完整版本，不存在中间态 |
| 损坏文件**改名隔离**（`.corrupt-<ts>`） | 新增 `_quarantine_corrupt` | 即使损坏也保留原字节供抢救；不再被空列表覆盖 |

测试 `tests/test_feedback_durability.py`（9 条）钉死两条不变式：
写入失败时原文件必须不变、读到损坏时原字节必须被保留。

## 三、注数「永远固定在最大值」：三层原因

### 3.1 上限被硬编码，而生产配置恰好顶在上限

```python
MAX_TICKETS_DIGITAL = 50      # 数字型
MAX_TICKETS_LOTTO = 200       # 乐透型
```

而生产配置是 `fixed.双色球 = 200`、`fixed.排列3 = 50` —— **两个都正好等于上限**。
前端滑块的 `max` 直接取这个值，于是往右拖到底就拖不动了。

实测写入链路（临时 store，不动真身）：

| 操作 | 结果 |
|---|---|
| 保存 fixed 双色球 = 100 | 生效 100 ✓ |
| 保存 fixed 双色球 = **300** | 生效 **200**（被截断） |
| 保存 fixed 排列3 = **80** | 生效 **50**（被截断） |

### 3.2 动态策略会单向把注数推到上限，然后卡住

`decide_next_count` 原第 2 条规则：命中率 `|z| > 2` ⇒ **强制 +2 注**。
这条规则有两个问题：

**① 方向上不成立。** `E[中奖注数] = K·p`，加注只把注数按比例放大，
**单注中奖概率 p 恒定** ⇒ 命中率不会因为加注而回升。所以这条路径永远追不上，
只会单向爬到上限。

**② 样本量上不成立。** z 原用「注数」当 n，但同一批次内的票共享蓝球
（实测一批 ~88 注只覆盖 12/16 个蓝球），中奖事件强相关 ⇒ 有效独立观测 ≈ **批次数**。
实查 `lookback=500` 只覆盖 **4 批**：

| 批次 | 注数 | 覆盖蓝球 | 该批命中率 |
|---|---|---|---|
| 26118 | 95 | 15/16 | 2.11% |
| 26119 | 5 | 4/16 | 0.00% |
| 26120 | **200** | **16/16** | 2.50% |
| 26121 | **200** | **16/16** | 4.50% |

批均命中率从 0% 到 4.5% 剧烈跳动，名义 z = −3.14 完全由噪声撑起。

**后果**：双色球被一路推到 200 注上限（26120、26121 都是 200），
用户手动调小后下一期又被 +2 推回 —— 这就是「怎么调都固定在最大值」的直接体感。

### 3.3 调度器把注数在调度时刻固化

`web/scheduler.py:242` 原本写 `{"groups": resolve_groups(lottery)}`。
`resolve_groups()` 在**调度时刻**求值并固化成显式参数，而实际出号可能晚几秒到几分钟；
期间滑轨变了，出号仍用旧值。实测日志：

```
⚠️ 双色球 显式出号注数 84 ≠ 看板滑轨 86
⚠️ 双色球 显式出号注数 84 ≠ 看板滑轨 88
```

连报两条（两路触发并发），而 pending 最终落的是 **84 注**。
`web/startup_recovery.py` 有两处同构问题。

### 3.4 修复

| # | 改动 | 效果 |
|---|---|---|
| 1 | 上限改为**按彩种可配**（`DEFAULT_LIMITS` + `config/ticket_size.json` 的 `limits`，硬顶 `HARD_CAP=1000`） | 双色球 200→**500**、大乐透 400、七星彩 300、排列3/3D 200、排列5 100。保存 300 现在生效 300 |
| 2 | **移除「命中率 → 加注」整条路径**，偏离只写 `诊断` 字段 | 自动路径**永不加注**。双色球 88 → 88（原来是 90） |
| 3 | 偏离要求 `n_batches >= 20` 才作数，否则标注「样本不足，判为噪声」 | 4 批样本不再驱动任何调整 |
| 4 | 新增 `锁定` 开关（看板可勾） | 勾上后后台结算**不会**改动注数；「立即按策略调整」按钮仍可手动触发 |
| 5 | 调度器/启动恢复**不再固化** `groups` | 出号时刻读最新滑轨，日志里的 84≠86 不会再有 |

上限取值依据：

- 双色球 `cap=3 + MAX_POOL=8000` 的选号硬约束约 **649 注**（Stage 0 实测），取 500 留裕度
- 大乐透同结构更宽（约 3,057 注），但出号耗时随 K 增长，保守取 400
- 数字型排列3/3D 直选空间 1,000 ⇒ 200 注 = 20%；排列5 空间 100,000 ⇒ 100 注

修复后钳制实测（`ts._clamp`）：

| 彩种 | 想设 | 实际 | 说明 |
|---|---|---|---|
| 双色球 | 300 | **300** | 原来被截到 200 |
| 双色球 | 800 | 500 | 触到彩种上限 |
| 双色球 | 1500 | 500 | 同上（未到 `HARD_CAP`，彩种上限先命中） |
| 排列3 | 80 | **80** | 原来被截到 50 |
| 排列3 | 500 | 200 | 触到彩种上限 |

上限要再放宽，改 `config/ticket_size.json` 的 `limits` 即可（无需改代码），最高 `HARD_CAP=1000`。

### 3.5 修复后实测

```

        诊断: 命中率 3.20% vs 理论 6.71%（名义 z=-3.1，但只有 4 批独立样本 < 20）⇒ 判为噪声，不改注数
大乐透  当前=38   上限=400  建议=38   样本够=False 批=12
```

## 五、全量回归期间又发现两处（与本次改动无关的既有缺陷）

跑 `pytest tests/ -q` 时才暴露，都不是本次改动引入的，但都会持续制造假信号，一并修掉。

### 5.1 `test_health_digest` 是日历依赖的 —— 每周日必挂

```
FAILED tests/test_health_digest.py::test_maybe_run_cold_start_has_own_slot
assert ['daily', 'full_health'] == ['daily']
```

`web/health_digest.py` 有 `FULL_HEALTH_WEEKDAY = 6`（周日跑六项全扫描），
而该测试用 `datetime.now()` 当基准 ⇒ **运行日恰好是周日时**，周检槽位会和日报槽位一起触发。

更糟的是：它会**真跑一遍全扫描**，把报告写进真实 `logs/`（本次就写出了 `项目体检_20261025.md`），
并从真实反馈目录读数据 —— 一个测试污染了生产产物。

修复（`tests/test_health_digest.py`）：

- 所有时点基准改为固定周三 `_at(hour, minute)`（`2026-10-21`，weekday=2 ≠ 6）
- `env` fixture 里把 `run_full_health` 兜底成桩，就算误落周检槽位也**不会真跑**

修后该文件 **22 passed，3.02s**（此前会卡几分钟真跑全扫描）。

### 5.2 排列3 一条旧记录的 `分区命中` 存值是错的

体检报 `排列3: 记录问题 1 条 — 分区命中不符@历史#28 期26215`。

查证：该记录是**旧格式**，`预测号码` 用 `百位/十位/个位` 命名，
`分区命中` 却按 `第1位/第2位/第3位` 存 —— 当年结算时两边没对上位置：

| 项 | 值 |
|---|---|
| 预测号码 | 百位 9 / 十位 8 / 个位 1 |
| 实际号码 | 第1位 **9** / 第2位 2 / 第3位 7 |
| 存储分区命中 | 第1位 **0** ← 错 |
| 重算应为 | 第1位 **1** |

不是审计误报，是真实存值错误。修复脚本 `scripts/oneoff/_fix_pa3_zone_hit.py`
（`--dry-run` / `--apply`，只重算 `分区命中` / `总命中`，写前备份、写后回读校验）：

```
排列3: 记录 2069 条，需修 1 条
  历史#28 期26215  分区命中 {第1位:0,...} -> {第1位:1,...}  总命中 0 -> 1
```

修后 `scripts/audit_records.py` 排列3 **0 条问题**，`scripts/health_check.py`
**真实待处理问题 0 项**（此前每天 23:40 都会推这条，属于长期噪声）。

> 双色球仍报 1 条「蓝球 个数=2≠1 @历史#5 期26090」，但该记录 `valid_prediction=False`，
> 属**既定隔离**（按设计不参与策略权重/战绩统计），日报不报，不动它。
