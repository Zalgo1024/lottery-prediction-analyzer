# 新数据库方案 · market.db（旁路并存版）

> 定位：**新增一个库，不替换、不改动现有 CSV 与读取链路**。
> 现有 `lottery_data/*.csv` + `data/loader.py` + 流水线全部保持原样，新库只做"第二真源"。

---

## 一、为什么值得再建一个库

现有 CSV 能跑，但有四个结构性限制，靠改 CSV 解决不了：

| 现状问题 | 具体表现 |
|---|---|
| 没有 schema | 列顺序靠代码猜；双色球 CSV 表头是 GBK，读出来是乱码 |
| 无法共存多源 | 同一期只能存一份，官方与 500 冲突时只能覆盖，无法比对 |
| 出球顺序无处存 | 中彩网给了 `seqFrontWinningNum`，CSV 里没有列，只能丢掉 |
| 地区维度无处存 | 财政部是"省 × 月"结构，和"期 × 号码"完全不是一个形状 |

SQLite 单文件、Python 标准库自带、零安装、可直接用 SQL 查——正好覆盖这四点。

## 二、五张表

```sql
PRAGMA journal_mode = WAL;

-- 1. 彩种字典
CREATE TABLE lottery (
  code        TEXT PRIMARY KEY,   -- ssq / dlt / pl3 / pl5 / qxc / sd / qlc / kl8
  name        TEXT NOT NULL,      -- 双色球 / 大乐透 ...
  family      TEXT NOT NULL,      -- cwl / sporttery
  issue_width INTEGER,            -- 期号宽度（排列5=5，双色球=7）
  zones       TEXT                -- JSON：[{name,min,max,count}]
);

-- 2. 开奖主表（★ source 进主键，同源多份并存）
CREATE TABLE draw (
  lottery    TEXT NOT NULL REFERENCES lottery(code),
  issue      TEXT NOT NULL,      -- 原样存，不补零
  source     TEXT NOT NULL,      -- cwl / sporttery / zhcw / 500
  draw_date  TEXT,               -- ISO: 2026-10-20
  front      TEXT,               -- JSON 数组，排序后
  back       TEXT,               -- JSON 数组
  seq_front  TEXT,               -- 出球顺序（仅 zhcw 有，其余 NULL）
  seq_back   TEXT,
  sales      INTEGER,            -- 元
  pool       INTEGER,            -- 元
  fetched_at TEXT NOT NULL,
  PRIMARY KEY (lottery, issue, source)
);

-- 3. 奖级明细
CREATE TABLE prize (
  lottery    TEXT NOT NULL,
  issue      TEXT NOT NULL,
  source     TEXT NOT NULL,
  level      INTEGER NOT NULL,   -- 1..N
  level_name TEXT,               -- 一等奖 / 直选 / 组选3 ...
  winners    INTEGER,            -- 中奖注数
  amount     INTEGER,            -- 单注奖金（元）
  PRIMARY KEY (lottery, issue, source, level)
);

-- 4. 分省月销量（财政部）
CREATE TABLE region_sales (
  ym             TEXT NOT NULL,  -- 2026-06
  region         TEXT NOT NULL,  -- 北京 / 广东 ...
  agency         TEXT NOT NULL,  -- 福彩 / 体彩
  sales_wan      REAL,           -- 当月，万元
  yoy            REAL,           -- 同比 %
  cumulative_wan REAL,           -- 本年累计，万元
  source         TEXT DEFAULT 'mof',
  PRIMARY KEY (ym, region, agency)
);

-- 5. 多源对账差异
CREATE TABLE reconcile (
  lottery    TEXT, issue TEXT, field TEXT,
  src_a TEXT, val_a TEXT, src_b TEXT, val_b TEXT,
  agree      INTEGER NOT NULL,   -- 1 一致 / 0 冲突
  checked_at TEXT NOT NULL
);

-- 便捷视图：按期号取"最可信"的一条（源优先级 官方 > 中彩网 > 500）
CREATE VIEW v_draw AS
SELECT * FROM draw d
WHERE source = (
  SELECT source FROM draw x
  WHERE x.lottery = d.lottery AND x.issue = d.issue
  ORDER BY CASE source WHEN 'cwl' THEN 0 WHEN 'sporttery' THEN 0
                       WHEN 'zhcw' THEN 1 ELSE 2 END
  LIMIT 1
);
```

## 三、四个关键设计决定

**1. `source` 放进主键，而不是当一个普通列**
一期开奖在 cwl、中彩网、500 三个源各存一行。冲突不会覆盖，而是能被 `reconcile` 查出来。
这是"多源可对账"的前提，也是这套方案相对 CSV 最大的价值。

**2. 期号原样存字符串，不补零、不转 int**
现有 CSV 里排列5 是 `04001`（5 位），双色球是 `2026120`（7 位）。如果新库做归一化，
两边口径立刻打架。原样存，宽度由 `lottery.issue_width` 描述，比较时再处理。

**3. 号码存 JSON 文本，不拆成 号码1..号码20 的列**
快乐8 一期 20 个号，双色球 7 个，七星彩 7 位（第 7 位可到 14）。定长列表格必然要为最长者留 20 列，
其余全空。JSON 一列解决，且 SQLite 有 `json_each()` 可直接展开查询。

**4. 出球顺序单独成列**
`front` 是排序后的号码集合，`seq_front` 是球被摇出来的顺序。两者**不是同一个东西**，
不能合并。现有四条机制轨全部基于 `front`，`seq_front` 是一条从未被使用的独立数据。

## 四、体积估算（不是拍脑袋）

- 6 彩种合计约 **2.3 万期**
- 每期平均 6 个奖级 → 约 **14 万行**
- 每行含号码与金额文本 → SQLite 约 **40–60 MB**

对比现有：`logs/automation/status.json` 一个 JSON 就 816 KB，
`lottery_data/` 全部 CSV 合计约 8 MB。新库 60 MB 属于可接受范围，且查询快一个数量级。

## 五、落地步骤（每一步都可单独回退）

| 步 | 做什么 | 影响 |
|---|---|---|
| 1 | `market/build.py`：建库 + 把现有 6 个 CSV **只读**导入（source='500'） | 只新建一个 .db 文件 |
| 2 | `market/sync.py`：按官方源增量拉取，按 source 写入 | 只写新库 |
| 3 | `market/reconcile.py`：官方 vs 500 逐字段对账，差异进 reconcile | 只读双方 |
| 4 | CLI 暴露 `python cli.py market check` | 不接 Web、不接流水线 |

**第 1 步的关键约束**：导入现有 CSV 时**不修改 CSV 一个字节**，只读。
任何一步出问题，删掉 `market.db` 即完全回到现状，零残留。

## 六、明确不做（防止变成"替换"）

- ❌ 不改 `data/loader.py`、不改流水线读取路径
- ❌ 不改 `lottery_data/*.csv` 的任何列或内容
- ❌ 不引入 ORM、不引入第三方依赖（只用 `sqlite3` 标准库）
- ❌ 不在 Web 看板上暴露新库，除非前三步稳定跑满两周
- ❌ 不把新库设为默认数据源

真正切换的唯一条件：**对账连续两周零差异**，且你明确同意。在那之前它只是一个旁路校验库。

---

## 七、它先把哪两件事变可能

1. **多源交叉验证**：同一期三个源对不上时能立刻发现，而不是等到策略算错才回头查。
2. **出球顺序进入测量**：现有 `ev/mechanism` 四轨只看号码集合，`seq_front` 是全新的可用维度。
