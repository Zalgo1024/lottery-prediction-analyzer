> **一套把「看起来有效」和「真的有效」分开的检验框架 · 彩票是最严苛的压力测试场**

![Python](https://img.shields.io/badge/Python-3.10%2B-3776AB) ![Tests](https://img.shields.io/badge/pytest-2496%20passed-3B6D11) ![Lotteries](https://img.shields.io/badge/%E5%BD%A9%E7%A7%8D-6-854F0B) ![License](https://img.shields.io/badge/License-AGPL--3.0-blue)

## 这个项目真正解决的问题

时序分析里最常见的失败不是算错，而是**把噪声读成信号**：试 20 个指标，总有一个 p<0.05；
在三千期数据上换 50 种切分，总有一次回测曲线漂亮。这不是水平问题，是多重比较的数学必然。

所以本框架的重心不是「能不能预测下一期」，而是**凭什么相信某个结论**。
任何「这个特征有效」「这条策略能赚钱」的主张，都必须走完五道工序（`credibility/` + `discovery/`）：

```
预注册（先固定假设与终点，不许事后挑）
  → 严格样本外回测（滚动窗口，评估段从未参与优化）
  → 随机基线军团（同池随机多次，与策略同尺度对照）
  → 效应量门控（统计显著 ≠ 经济上可用）
  → FDR 多重比较校正（BH，控制错误发现率）
```

五道全过才写进结论；**没过的记为「未检出」**——数据不足、功效不够、确实不存在
是三件不同的事，混为一谈只是另一种自欺。

## 为什么拿彩票当试验场

判据硬：规则公开、样本大（全部彩种合计三万余期）、每期独立且无协变量、结果逐期可核验。
一套检验方法在这里都跑不出稳定信号，在噪声更大的业务数据上更不会有奇效；
反过来，能在这里穿过五道闸的东西，才有资格拿到别处去试。

围绕这个试验场，项目把整条链路做到了生产可用——**检验层是目的，其余是让检验能被验收的配套**：

- 📊 **数据管道（彩种清单以 `config.LOTTERY_CONFIG` 为准）**：双色球/大乐透/排列5/福彩3D/排列3/七星彩/七乐彩/快乐8——抓取、清洗、完整性体检、外部逐期核对
  · 七乐彩：7 个基本号（1–30）+ 1 个**特别号**（从剩余 23 个摇出，票面不含）
  · 快乐8：80 选 20 开出，票面按 10 种玩法选 1–10 个；39 档奖级全部为「规则约束值」（含限赔/封顶）
- 🖥️ **Web 看板（17 页面）+ CLI 双入口**：统计/训练/预测/命中历史/期望时机/证据看板（`/audit`）/盈利账本（`/ledger`）
- 🎯 **预测-评估闭环**：按滑轨注数出号（看板可调）→ 开奖自动评估命中/奖级（含单注奖金）→ 策略权重自适应
- ⚖️ **测量与证据看板**（`/audit`）：开奖质量、EV 看板（限号/撞号修正）、P/L 反馈、距离与实得画像、A/B 对照、中奖归因、机制缝隙四轨、策略鲁棒性（压力检验）；每张卡自带「在测什么 / 名词 / 口径与诚实边界」，配名词速查
- 🔬 **机制缝隙测量**（`ev/mechanism/`）：四轨量「开奖是否偏离等可能」——只给效应量、CI 与判定，并固定一条表述纪律：**未检出 ≠ 已证明公平**（见下文）
- 📈 **期望时机**：Rollover-EV 分析——奖池滚存是本场景中唯一与选号无关的数学杠杆
- 🤖 **自动流水线**：三路触发（调度 / 事件 / 自愈），无人值守，见下文「自动化」

## ★ 数据文件详解

### 1. `lottery_data/` —— 历史开奖（唯一数据源，抓取自 500.com）

| 文件 | 内容 |
|---|---|
| `双色球历史数据.csv` / `大乐透历史数据.csv` | 乐透型全历史开奖（2003/2007 至今），含奖池与一二等奖金 |
| `排列5/排列3/福彩3D/七星彩历史数据.csv` | 数字型全历史开奖（按位有序） |
| `{数字型彩种}销售奖级数据.csv` | 销售额、奖池、一等奖注数/单注奖金（EV 分析用） |
| `双色球/大乐透历史数据_cleaned.csv` | `clean` 命令产物，loader 优先使用 |
| `七乐彩/快乐8历史数据.csv` | 由 `market/market.db` 派生（`scripts/export_lottery_csv.py`），不是从 500.com 抓的 |

> ⚠️ 七乐彩与快乐8 的历史 CSV 是**派生文件**：真源是 `market/market.db`，
> 导出脚本会写 `_<彩种>_export_meta.json` 记录来源与行数。要更新它们，
> 先跑 `python -m market.update`，再跑 `python scripts/export_lottery_csv.py`。
> 直接手改 CSV 会在下次导出时被覆盖。

**列结构：**

- 乐透型（双色球示例，15 列）：
  `期号, 红球1..红球6, 蓝球1, 奖池奖金(元), 一等奖注数, 一等奖奖金（元）, 二等奖注数, 二等奖奖金（元）, 总投注额(元), 开奖日期`
  大乐透为红球 1-5 + 蓝球 1-2。⚠️ **开奖日期格式为 `D/M/YYYY`（日在前、月在后，不是美式 `M/D/YYYY`）**
  ——例：`23/2/2003` = 2003-02-23（日 23 > 12，可直接判读）。解析口径见
  `data/schema.py::parse_draw_date`，写出口径见 `data/cleaner.py`。
- 数字型（福彩3D 示例）：
  `期号, 开奖日期, 号码1, 号码2, 号码3`（排列5/七星彩列数相应为 5/7，日期为 `YYYY-MM-DD`）

> 注：`lottery_data/` **已纳入版本控制**（约 3.3MB，作为数据备份；`_backup_*/` 与 `*.bak` 除外），
> 虽也可从 500.com 重建。已知唯一缺口：排列5 期 04006/04007（数据源本身缺失）。

### 2. `training/feedback/` —— 预测-评估闭环（自动生成）

| 文件 | 内容 |
|---|---|
| `{彩种}_pending.json` | **待开奖预测**：目标期号、预测模式、号码组数、预测号码数组（策略/置信度/评分明细/号码） |
| `{彩种}_feedback_history.json` | **已评估命中记录**：期号、预测 vs 实际号码、红/蓝/总命中、`中奖等级`、`valid_prediction`（非法票隔离标记）、`记录类型`（预测/训练）、评估时间 |
| `{彩种}_strategy_weights.json` | **策略权重**：开奖后按真实命中自适应更新 |

## 彩种口径：七乐彩与快乐8

这两个彩种的**几何结构与既有六彩种不同**，口径不写清就会被误读。判据都在测试里，
本文只做指针（数字写死在这里会脱管）。

### 七乐彩（`qlc`，2007-01 起）

- 开奖 = **7 个基本号 + 1 个特别号**（基本号 1–30 摇出 7 个，特别号从**剩余 23 个**里摇 1 个）。
- **票面只有 7 个基本号，不含特别号**。配置里用 `draw_only` + `draw: 1` 表达
  （`Zone.choose` 是「票面选几个」、`Zone.draw_count` 是「开奖摇几个」，两者故意分开）。
- 判级看 `(命中基本号 h, 票面是否含特别号 j)`；`h=6,j=1` 与 `h=7` 等档位的概率
  **不能用通用组合式**（通用式假设"开奖也是 w 个号"，会把六等概率算错 2/3）。
  精确式写在 `ev/payout._probs_qlc`，偏差对照见该函数 docstring。
- 一~三等为浮动奖（按当期奖池公布单注金额），四~七等为固定奖（200/50/10/5 元）。
- 判据：`tests/test_qlc.py`、`tests/test_regulated_amount.py`。

### 快乐8（`kl8`，2020-10 起）

- **80 选 20 开出**，票面按 **10 种玩法**（选一~选十）选 1–10 个；奖级只看"命中几个"。
- 10 个玩法**没有拆成 10 个彩种**：pending/账本/预算/停发联锁/推送全部以「彩种」为键，
  拆开会把注数、额度、台账、`health()` 一起乘 10。玩法维度由
  `LotterySchema.plays` + `picks_for(play)` 承载，默认「选十」。
- **39 档奖级没有一档是真固定**：全部是「规则名义值 + 限赔/封顶」。
  同一档在不同期会不同（如 x9z9 名义 30 万、2026 年多期为 25 万；x7z7 名义 1 万、2026 年 8500）。
  ⇒ 单注金额**必须**走 `ev/profit/amounts.grade_amount`（当期实测 → 名义回退并标注来源），
  不能按名义值算返奖率。
- **选七~选十「中 0 个」也中奖**（2 元）⇒ 命中数 0 不能直接判「未中」。
- **日开**（约 30 期/月）⇒ 月度期数、注数上限、预算包络都按 30 期口径，
  不能沿用 13 期彩种的 500 注兜底。
- 名义返奖率约 57.5%，**明显高于双色球/大乐透的约 50%**（这是规则设定，不是本仓的估计）；
  实测金额（限赔后）只会更低，因此 README 里「单注长期 EV ≈ −50%」需按彩种分别读。
  锚点见 `tests/test_kl8.py::test_nominal_return_rate_is_about_57_5_percent`。
- 判据：`tests/test_kl8.py`、`tests/test_regulated_amount.py`、`tests/test_schema_draw_zones.py`。

### 两者共同的「不适用」边界

| 环节 | 是否适用 | 原因 |
|---|---|---|
| 机制缝隙 A/B 轨（`ev/mechanism/`） | ❌ 不适用 | 该轨需要「一等奖注数 / 二等奖注数 / 总投注额」三列；两彩种的 CSV 只有号码。原因表在 `ev/mechanism/common.NOT_APPLICABLE`，由测试锁定 |
| 按实得奖金选号（`cli.py select`） | ❌ 显式拒绝 | 其排序键来自 `ev.engine.net_ev`（只覆盖数字型）；这两彩种单注 EV 与选号无关 ⇒ 排序无信息量 |
| 实得口径表（`cli.py payout`） | ✅ 适用 | `cli.py payout 快乐8 --nums 1,2,...,10 [--play 选九]` / `cli.py payout 七乐彩 --nums 1,2,3,4,5,6,7` |
| 生产出号 / 结算 / 账本 / 推送 / 体检 | ✅ 适用 | 注数分别为 5 注/期（与最小安全值一致） |

### 彩种字面量清扫（2026-11-02）

全仓曾散落 20+ 处手写彩种清单，漏一处**不会报错**：彩种会静默消失（payout 返回 error、
EV 退化到名义值、预算上限回落到 500）。逐个判定结果：

| 处理 | 位置 | 判据 |
|---|---|---|
| **加键** | `config.LOTTERY_CONFIG`、`data/ticket_size.DEFAULT_LIMITS`、`ev/budget_envelope.PERIODS_PER_MONTH`、`ev/payout._LOTTERY`、`data/audit/checks.LOTS`、`data/push_notify.ALL_LOTTERIES`、`web/routes/{audit,ledger}._ALL`、`scripts/{rebuild_ledger,backfill_money,preview_push}` | 运行时/账本/推送按彩种遍历，缺一处即丢彩种 |
| **加键（数据口径）** | `cli.py changepoint` 默认清单 | 纯数据扫描，不依赖 EV/奖级表 |

### 更新槽位：一次只能跑一个源，但排队 ≠ 失败（2026-11-02）

`market/update.run_update` 的槽位是**全进程唯一**的（一个 `_RUNNING` + 一把
`.update.lock`）。而启动自愈会**同时**给多个彩种触发流水线：七乐彩走 `zhcw`、快乐8 走
`cwl`，两个源互不相干，却共用同一个槽位 ⇒ 后到的直接判 `busy` ⇒
`data/fetcher._update_via_market` 只能返回 error ⇒ 流水线抛「抓取失败: …本次未抓取」
⇒ **该彩种这一轮没有任何 pending**。2026-11-02 02:31 的日志就是这两条（互相把对方挡了）。

`run_update(..., wait_sec=N)` 现在是排队：占不到就每秒重试，拿到就干活，超时才照实报错
（文案带「已等待 X 秒」）。`_update_via_market` 传 180 秒，并把实际等待记进
`waited_sec`。默认 `wait_sec=0` 保持旧语义 —— 页面按钮这类入口**不该**排队。

回归护栏：`tests/test_market_update.py` 四条（0 秒立刻失败且文案不变 / 排队后继续干活 /
超时如实报错 / 进程内标志也排队）。

### 统计口径：「每期取号数」只有 `zone.draw_count` 一个真源（2026-11-02）

抽查七乐彩/快乐8 的随机性审计时发现三处研究模块共用一个错假设：**每期取号数 = 票面 `choose`**。
对原来 6 个彩种恰好成立（`draw` 全是 `None`，`draw_count` 退回 `choose`），对这两个恰好不成立：

| 彩种/分区 | 票面 `choose` | 开奖 `draw` | 用 `choose` 的后果 |
|---|---|---|---|
| 七乐彩 / 特别号 | **0**（draw_only） | 1 | `exp = n·0/K = 0` ⇒ 卡方 `0/0` 变 `inf` ⇒ **假报「实质偏离 q=0.0392」**。一个纯算术产物被当成开奖异常 |
| 快乐8 / 基本号 | 10 | **20** | `p0` 只有真实值的 1/2 ⇒ 每个号都像"出现翻倍" ⇒ 财富过程指数发散，实见 `e-max=3.6e31` 的假告警 |

修法是统一走 `data.schema.Zone.draw_count`（已封装「`draw` 优先、缺省 `choose`」），并加一道
**数据交叉核对**：实测每期取号数与配置不符时，照实测跑并把这件事写进 `注`，不静默采用配置值。

连带两件事：

- `credibility/randomness_audit`、`discovery/always_valid`、`discovery/info_theory` 的彩种清单
  也改成跟 `config` 同源（原来手写 6 个 ⇒ 报告里少两行，读者当成"没问题"）。
- Bonferroni 族规模 `M` 随之从 22 → **25** 个分区（8 彩种）。**不许把 M 写死**：
  写死等于"新彩种接进来、阈值还是旧的"，两边一起静默错。`tests/test_always_valid.py` 现在
  从注册表推导 M 并比对。

顺带清掉两处**未获得的结论**：审计结论原写「…获得权威背书」、e-value 结论原写
「『该彩种开奖分区边际公平』通过持续监控」。两者都是把"没检出偏离"说成"已被证明"。
现在统一为「仅表示已测维度在该样本量下未见异常，**不构成**对开奖公平性的证明」。

回归护栏（`tests/test_new_lottery_surfaces.py`）：零假设概率 `p0` 必须等于 `draw_count/size`、
指示矩阵每行非零数必须恒为 `draw_count`、`p 值`/`统计量` 必须有限、`draw_only` 分区不得被报偏离。

并固定一条表述纪律：**「未检出 ≠ 已证明公平」**。

| 彩种 | 判定轨 | 测量结果（2026-10-18 快照） | 裁决 |
|---|---|---|---|
| 双色球 | A/B | R=0.99391 [0.9640,1.0252]、ū=0.50135 [0.4908,0.5121]、γ=−0.0185（CI 含 0） | 未检出 |

### 策略鲁棒性：策略在模型失真后还剩多少优势（`/audit` 第 ⑨ 卡）

把「销售信息缺失、拥挤度估计偏差、热度标签错标」当成不确定情景，比较盈利排序策略与
**等注数随机基线**的回款差，看这点优势在模型失真后还剩多少。它检验的是策略的可信度，
不是中奖能力。

- **口径**：`ev/profit/stress` 用**扰动后的分数选号、用基准分数评估** —— 否则量到的是
  「扰动后模型的自评」，而不是真实还剩多少优势。保留率 = 该情景优势 ÷ 基准优势。
- **两个必须守住的细节**：① 无信息时所有票的 EV 相等 ⇒ 用**种子化 jitter** 打破平局，
  否则 `argsort` 会按行号选中固定组合，测出假的负优势；② 均匀缩放分数只改幅度不改排序
  ⇒「偏差」必须用**局部错标**来测（均匀缩放时保留率恒为满值，什么都测不出来）。
- **结论**：只有双色球有可测优势，且**完全依赖热度模型的准确性** —— 错标比例升高时优势
  单调衰减，没有拥挤度信息时归零。其余彩种不是「测了没问题」，而是**结构上没有可测的东西**
  （无浮动奖、热度模型未达 Go 门槛、倾斜来源是未检验代理）。
- 结果落 `logs/automation/strategy_robustness.json`（夜间日报刷新）。看板第 ⑨ 卡与
  `/api/audit/robustness` **只读缓存、不在页面里触发测量**（一次约 40 秒）。
- ★ 缓存里**每个彩种都有一条**：能测的给判决，不能测的给**理由**。只写「测了的那个」会让
  看板显示成一行，读者无从分辨其余彩种是「没测」还是「通过了」—— 缺席不等于通过。
- ★ 与 `/robustness` 页不是同一件事：那一页是盈亏四轴（β 形状／销量带／池模型／税口径）的
  **敏感性**；本卡是「策略 vs 随机基线」的**优势存活检验**。
- `cli.py profit <彩种> ... --stress` 可把该判决接进决策流：闸门**只降不升**，上游
  `条件性可参与` ∧ 鲁棒性`退化/无优势` ⇒ 降为 `本期不建议参与`；默认关闭，不传时返回逐位相同。

## 自动化

系统全程自动运转，无需人工干预：每天自动抓新开奖、评估昨日预测、更新策略权重、生成下一期预测、刷新看板。

### 三个触发路径（统一入口 `web/utils.py::run_auto_pipeline_core`，口径一致、并发去重，绝不重复跑）

| 路径 | 实现 | 机制 |
|---|---|---|
| ① 定时调度 | `web/scheduler.py` | 每个彩种**开奖日 22:05** 自动触发；如果 22:05 时应用没在运行，之后启动会**补跑当天漏掉的**（按「最近一个应触发的开奖日 22:05」判定，不顺延到明天）；21:00–23:00 间还有晚间滞后补跑兜底 |
| ② 事件驱动 | `web/worker.py` | worker 持续轮询数据目录，发现新开奖 → 立即入队评估与流水线任务（非每日开奖的乐透型为主，数字型每日开走调度即可） |
| ③ 启动自愈 | `web/startup_recovery.py` | 应用每次启动时：对比各彩种看板快照期号 vs CSV 最新期，**落后就补跑**；顺带补抓缺失数据 |

#### Windows 计划任务（`scripts/auto_scheduled.ps1`，与 ①②③ 并行的第 4 条入口）

22:05 主任务 + 白天每 3 小时兜底（只补数据滞后的彩种）。彩种清单是**手写**的，
所以它必须与 `config.LOTTERY_CONFIG` 的 `draw_days` 一一对上：

| 脚本里的 `$dow`（.NET：**周日=0**） | 彩种 | `draw_days`（Python weekday：**周一=0**） |
| --- | --- | --- |
| `@(2, 4, 0)` | 双色球 | `[1, 3, 6]` |
| `@(1, 3, 6)` | 大乐透 | `[0, 2, 5]` |
| `@(2, 5, 0)` | 七星彩 | `[1, 4, 6]` |
| `@(1, 3, 5)` | 七乐彩 | `[0, 2, 4]` |
| 每日数组 | 排列5 / 福彩3D / 排列3 / 快乐8 | `[0..6]` |

> ★ **两套星期编码**：PowerShell 的 `[DayOfWeek]` 周日=0，而 Python `weekday()` 周一=0，
> 换算 `(weekday + 1) % 7`。抄错照样跑得通，只是那天跑错彩种，且只在特定星期几才露出来。
> ★★ 七乐彩、快乐8 曾**不在这个清单里**（脚本手写 6 个彩种）—— 一旦任务被启用，这两个
> 彩种就永远不会被它跑，而日志里没有任何一行说"跳过了谁"（典型静默缺席）。
> 现由 `tests/test_lottery_registry.py::test_ps1_schedule_covers_all_lotteries_with_correct_weekdays`
> 锁死：清单必须等于注册表，且每天的星期映射逐条核对 —— 少一个、错一天都会红。
>
> ⚠️ **本机现状（2026-11-03 实测）**：`config/` 里没有该任务的注册记录、
> `logs/auto_scheduled.log` 最后一行停在 2026-09-28，`Get-ScheduledTask` 也搜不到
> 引用本目录的任务 ⇒ **这个脚本当前并未被计划任务调用**。夜间流水线实际由
> `web/scheduler.py`（Flask 进程内，按 `draw_days` 遍历注册表 ⇒ 本来就覆盖 8 个彩种）
> 承担。补齐本脚本是为了「重新启用时不再漏彩种」；要真正启用需要重新注册任务
> （注册需要管理员权限，本仓库没有附带安装脚本）。

```
抓取最新开奖（500.com，含奖池/奖金回填）
  → 评估 pending 预测（写入命中/奖级/策略权重）
  → 预测下一期（注数走「出号数量」滑轨的当前生效值；目标期已有预测且组数一致则跳过，
    组数不一致则**另起一批**，不覆盖旧号 —— 见「重新出号」一节）
  → 异常检测 → EV/期望快照
  → 写 logs/automation/status.json（看板首页卡片的数据源）
```

### Worker 任务队列（`web/worker.py`）

- **任务类型**：`auto_pipeline`（流水线）、`evaluate`（评估）、`predict_tiered`（三档预测）、`robustness_full / robustness_light`（鲁棒性）
- **串行纪律**：同一时刻只执行一个任务，前一个没跑完只做心跳续期、不认领新任务
- **心跳与孤儿回收**：执行中任务每 30 秒续一次心跳；超过 10 分钟无心跳的 running 任务视为孤儿，启动时与周期性自动标为 failed
- **状态文件**：`config/worker_state.json`（pid/心跳/当前任务，看板可读）

### 出号数量：固定 / 动态（`config/ticket_size.json`）

看板首页「出号数量」卡提供每个彩种的滑轨，控制**每期出几注**。
**滑轨值即最终出号注数**（2026-10-11 起）：此前入账前还会按
`TICKET_COMPRESS_KEEP_RATIO=0.4` 再砍一刀，使滑轨设 176 实际只出 64 注，
与本卡文案「每次出号几注，由你决定」矛盾；现已在生产路径改为以出号数量为准
（`compress_tickets(..., target_count=目标注数)`，目标 ≥ 候选时不削减）。

| 模式 | 行为 |
| --- | --- |
| **固定数量** | 每次出号恒等于设定值（下限 1，**上限统一 500**，卡片右上角会标） |
| **动态数量** | 随每期评估自适应：命中率显著偏离理论值（\|z\|>2 个标准误）时回补 +2 注，其余情形维持当前注数（硬下限 1 注） |

> **上限统一 500**（2026-11-02 用户要求）。此前是逐彩种给值（双色球 500 / 大乐透 400 /
> 七星彩 300 / 福彩3D·排列3 200 / 排列5·快乐8 100），卡片上出现五种刻度，用户得逐格记
> 哪里能拖到哪 —— 那是**操作成本**，不是安全收益。更早的文档还写成「数字型 50、乐透型 200」，
> 与卡片真实值对不上，属文档失真。
>
> ★★ **上限 ≠ 可以随便买**。真正的硬约束是 `config/budget_aggregate.json` 的
> `月度总额` 与 `单期上限`（闸门启用时，见下文「预算包络」）：8 个彩种全按 500 出号
> 是 **172,000 元/月**（4 个 13 期彩种 52,000 + 4 个日开彩种 120,000），约为当前
> 月度总额 61,330 元的 2.8 倍 ⇒ **月中就会停发**。改上限只放开可拖拽范围，
> 不改实际出号注数（那由滑轨值 / 动态值决定）。
>
> **额度在哪里看**：就在这张卡的滑轨下面一行「本月预算：已投 X / 额度 Y，剩余 Z」，
> 剩余低于两成变橙、用尽变红并直接写「本期会停发」。此前闸门在界面上**没有任何出口**，
> 用户只能翻 `config/budget_aggregate.json`，额度用尽时的表现是「某天起忽然不出号」，
> 而滑轨值照样显示得正常 —— 这类「看起来正常、实际已停发」正是最该避免的失真。
> 数据源：`GET /api/settings/ticket-size` 的 `预算` 字段（只读，不参与任何决策）。

> 动态模式的**下调**信号原是「上一批压缩冗余淘汰占比」；2026-10-11 改为
> 「出号数量 = 最终注数」后不再产生压缩，该信号随之失效，动态模式目前只保留
> 命中率安全阀（不再自动下调）。若要恢复自动调节，需要引入新的冗余判据。

配置经 `config.resolve_groups` 统一下发，自动流水线 / 内置调度器 / worker / 启动恢复 /
CLI / Windows 计划任务六条路径全部生效；`python cli.py predict <彩种> --groups N` 仍可临时绕过。
下一期若已有 pending 预测，**组数与当前出号数量一致才复用**，不一致则按新数量重新生成
（避免改了滑轨却不生效）。

```bash
GET  /api/settings/ticket-size          # 各彩种当前值/上限/默认 + 动态建议
POST /api/settings/ticket-size          # {"mode":"fixed|dynamic","fixed":{...},"dynamic":{...}}
POST /api/settings/ticket-size/apply    # 动态模式：立刻按策略算一次并应用
POST /api/settings/ticket-size/reset    # 恢复默认（数字型 5 / 乐透型 100）
```

**诚实边界**：改注数只改变成本与规模，单注中奖概率恒定（期望线性性），整体 EV 仍为负；
动态下调不是"预测更准"，只是省钱与冗余控制。

#### 保存不生效的两道闸（2026-11-02）

用户报障：「改了七乐彩 / 快乐8 的注数，点保存又自己变回 5」。根因不在后端，而在
前端收集：原实现用**彩种在 JS 数组里的下标**拼 DOM id（`ts-num-${tsIdx(lottery)}`），
而 `Array.prototype.entries()` 给的是 `[下标, 值]` —— 解构写成 `for (const [lot, i] of ...)`
时 `lot` 拿到的是下标、`i` 才是彩种名，拼出 `ts-num-双色球`（不存在）⇒ 收集结果恒为
空对象 ⇒ 请求体是 `{"mode":"dynamic","dynamic":{}}`：**语法合法、字段合法、业务上也合法**
（等于什么都不改），于是接口返回成功、页面重渲染回原值，两端都不报错。

现在三道闸同时存在，任何一道单独都足以挡住这类静默失效：

| 层 | 闸 | 失效时表现为 |
| --- | --- | --- |
| 渲染/收集 | 输入框只带 `data-role`（range / num / cur）+ `data-lottery`，**不再有任何下标映射**，按属性值定位元素 | 不再有"撞 id / 拼错 id"这类错误来源 |
| 前端保存 | 收集到的彩种数必须等于页面渲染的彩种数，不等就**拒发请求**并弹窗说明 | 不再出现"提交了但什么都没改" |
| 服务端 | 对应模式的字段若为空字典，直接 400 拒绝 | 旧版前端/第三方调用也挡得住 |

`tests/test_ticket_size_collect_contract.py` 用静态契约锁住这三处（源码级检查，
不执行 JS）；**运行时证据另做**：真实 Chrome 改值 → 读 `config/ticket_size.json`
确认落盘，两者缺一不可 —— 静态测试只证明"代码长得对"。

### 重新出号：同一期多批并存（2026-11-02）

「出号数量」卡里每个彩种都有「重新出号」按钮（`POST /api/predict/regenerate`）。
语义是**多一批可选的票**，不是替换：

| 需求 | 实现 |
| --- | --- |
| 旧号不删除、随时可查 | pending 去重键由 `(目标期号, 档位, 台账域)` 扩为 **`+ 重出批号`**，同一期可并存多批，各自独立结算 |
| 新号优先 | 当期展示 / 推送 / 组数核对统一走 `latest_production_pending`（按记录时间取最大）⇒ 天然取到最新一批 |
| 旧号那边的奖也要拉出来 | 结算遍历**全部** pending；历史侧 `_fb_key` 同样带上「重出批号」，两批票面即使完全相同也各留一条（数字型空间小，必撞） |
| 两批票记两笔钱 | 预算台账幂等键同样带「重出批号」（`ev/budget_gate._rec_key`）。不带就会把第 2 批**覆盖**成第 1 批那一行 ⇒「本月已投」偏低 ⇒ 闸门比配置更松，且不报错 |
| 注数用哪个值 | **不传 `groups`**，一律走 `resolve_groups` ⇒ 用你刚保存的滑轨值，不会出现"滑轨改成 30、重出还是 5 注" |

```bash
POST /api/predict/regenerate   # {"lottery":"七乐彩"}
# → {ok, task_id, 目标期号, 重出批号, 上一批注数, 说明}
```

几条纪律：

* **首出批不写该字段**（老记录形态不变）；`重出批号 = 0` 与缺字段等价，不会被拆成两批。
* `next_renumber()` **推不出期号时不按期号过滤**，读盘异常时返回时间戳而不是 1 ——
  返回 1 会与已有第一批撞键，把「重新出号」退化成「覆盖出号」，正是这个按钮要防的事。
* **自动路径同口径**：`web/utils.py::run_auto_pipeline_core`（调度器 / worker / 启动自愈
  三条路径的公共入口）与 `cli.py auto` 在「已有批组数 ≠ 滑轨」时都**另起一批**而不是覆盖；
  试算（`record_pending=False` / `--no-record`）不递增批号，否则点几次试算就把真正第一版
  号码顶成「第 3 批」。
* 批号同 `renumber_scope()`（ContextVar）传递，而不是给 `predict()` 加参数：真正写
  pending 的是 `predict` 内部的四条返回分支，而这条需求与「怎么选号」毫无关系。
* **不改变任何概率**：多批只是多买票，单注中奖概率恒定、整体 EV 仍为负。同一期买两批
  意味着中奖事件的**重复计数**（`Σ pᵢ` 相加，不是并集），所以每批必须可区分、可追溯。
* ★ **已知边界（未修）**：`clamp()` 的「重生成不递缩」回补按「该彩种该期最近一条台账」
  取金额，而它拿不到重出批号 ⇒ 重出时会把上一批的金额也加回可用额度（约一批票的额度）。
  影响有界（只在用户点重出时发生、且 auto 来源仍受基线约束），但不是零 —— 若日后要
  收紧闸门，这里得把批号一路传进 `resolve_groups`/`clamp`。

#### 一组消息长什么样（2026-11-03 改版）

```
（双色球）彩票号码 / 中奖情况        ← 一行标签（组头）
> 仅供研究记录；在「开奖对全部组合等可能」的前提下…
[打开看板 · 调出号数量 / 看全部记录]
[开奖图 1 张]
[中奖（结算）图 M 张]
[号码（出号）图 N 张]              ← 500 注 = 10 页，按内容分页
（大乐透）彩票号码 / 中奖情况
…
```

* **组头只有一行标签**，按实际有哪几类图动态写：`彩票号码 / 中奖情况`、
  `彩票号码`、`中奖情况`、`开奖结果`。期号 / 注数 / 张数清单都删了 ——
  那些在图里都有（开奖图副标题、出号图元信息与组头、结算卡的奖级与奖金），
  堆在手机上要占 5~6 行，反而把「一眼分组」的作用抵消掉。
* **顺序固定：组头 → 开奖 → 中奖 → 号码**（改版前是 开奖 → 号码 → 中奖）。
* 组头**不加 `#` 一级标题**（企微的 H1 字号大、强制另起段落，一行标签会被折成两三行）。
* 诚实声明 `FOOTER_CONDITION` **一字未动**：它包含「开奖对全部组合等可能」这个前提与
  「未检出偏离 ≠ 证明开奖公平」，是单一真源，不因为「想短一点」而弱化。
  整条降级为纯文本时仍是完整版。

#### ★ 为什么以前「没有严格按顺序推送」

节流（`推送间隔秒`）只保证**两条之间隔多久**，管不住**谁插进来**。而
「立即运行全部」会一次起 N 个流水线线程（`web/scheduler.py::run_now` → `_launch`
不等待）、worker 事件触发 / 启动自愈 / 计划任务也会各自推送 —— 同一条 webhook 上，
A 彩种的组头与图片被 B 彩种的消息拆开。一组消息可达 21 条 × 3.2s ≈ 67 秒，窗口足够大。

现在 `push_lottery_images` 用 `_group_spin_lock()` 把「组头 + 全部图」圈成一个原子段：

| 层 | 手段 | 管什么 |
| --- | --- | --- |
| 进程内线程 | `threading.Lock` | 同一进程的多条流水线线程（「立即运行全部」是主要来源） |
| 跨进程 | `data/file_lock.py` 的 `config/.push_group.lock` | Flask 服务 + 计划任务各起一个 `cli.py auto` |

> ★ 两层**都是必需的**，不是冗余：`file_lock` 的 `open(lock_file, "a+")` 写在轮询 try 之外，
> Windows 上同一进程的第二个线程会直接 `PermissionError` —— 只靠文件锁时，同进程多线程
> 根本没有排队效果（`data/shadow.py` 记着同一条实测结论）。

其他纪律：

* **拿不到锁不丢消息**：降级为无锁发送 + warning + 结果里标 `lock=degraded-*`。
  组锁超时默认 420 秒（必须 < 调度器 600 秒等待窗口），可配 `组锁超时秒` / 关掉 `组级互斥`。
* `_pace_global` 的「读时间戳 → 算等待 → 写预约点」现在加了文件锁：
  原来两个进程可能读到同一个 `last` ⇒ 同时发出两条 ⇒ 企微超速**静默丢消息**。
* **失败不再误报成功**：原来是 `any(ok)`（21 条丢 20 条也算成功），现在 `_summarize()`
  区分「全部失败 / 部分失败 x/y / 全成功」，detail 直接显示在看板「最近推送·说明」。
* 推送日志补齐（原来 `data.push_notify` 的 INFO 全被丢弃）：每组打印
  `[PUSH] 组=双色球 序号=i/n 类型=image 段=号码 ok=True`，
  `grep "\[PUSH\]" logs/<日期>.log` 即可机械判断「有没有交错、有没有丢条」。

- Webhook 地址可整段粘贴，也可只粘 `?key=` 后面那串。
- token 回显一律掩码，掩码回传不会覆盖真实值；每日额度守卫（默认 0 = 不限，跨天清零）防刷屏。
- 「看板地址」选填（如 Tailscale 内网地址 `http://100.x.x.x:5000`），组头第二行附直达链接。
- **企业微信群机器人只能单向推送**，无法在群里改配置；调出号数量仍在看板完成。
- 未配置或网络异常一律降级为日志告警，绝不阻塞主流水线。
- 群机器人**没有 title 字段、图片消息也没有 caption** ⇒ 彩种名、期号、注数只能画进图里。

```bash
GET  /api/settings/push-notify          # 渠道/开关/掩码 token/最近推送/今日已推
POST /api/settings/push-notify          # {"provider":"wecom|pushplus|serverchan|off", ...}
POST /api/settings/push-notify/test     # 发一条测试消息（未配置返回 400）
```

**诚实边界**：推送只是通知渠道，不改变任何概率与 EV 结论。

## 维护（放着不管时会发生什么）

这个项目的设计前提是「不必天天开机」。开机后它会自己按顺序做：
抓数 → 补齐漏结算的期 → 核对简报新鲜度 → 核对注数并修复 → 推一条自检摘要。

之后每日本地生成一份**离线体检**（`logs/automation/digest_<日期>.json`，接口
`GET /api/system/digest?days=7`，看板「自动化运行状态」旁有摘要徽章）：

- **只在有问题时才推送**。正常静默 —— 每天一条"一切正常"只会被静音，
  真出问题时反而看不见。
- 检查项：流水线成功/失败次数、注数是否等于滑轨、各彩种数据滞后天数、
  下一期是否有预测。日志窗口写满时会标「计数可能偏少」，不把"至少这么多次"说成全量。
- 每周日额外跑一次六项全量体检（`scripts/health_check.py`）+ 清理 90 天前日志。

日常只需看一处：**看板标题旁的一致性徽章**。绿色 = 滑轨与实际出号对得上；
变红 = 有旁路改了注数。

常用脚本：

```bash
python scripts/sync_counts.py --check   # 文档里的测试数是否与真实一致
python scripts/sync_lock.py --check     # 依赖锁是否与环境一致
python scripts/prune_logs.py            # 预览可清理的旧日志（加 --apply 才删）
```
